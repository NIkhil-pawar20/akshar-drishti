How Akshar Drishti works, from upload to archive

A complete walk-through of the project in plain language: what happens to a page image at every step, which file and which function does each job, what each step hands to the next, and how all the files fit together.

1. The big picture

A clerk opens a web page, uploads a photo or scan of a government document, and clicks Process. About 6.7 seconds later (on a T4 GPU) the page shows: whether the document is signed and stamped, the full text in reading order, a table of key values such as dates and survey numbers, the Aadhaar and PAN numbers hidden, cropped pictures of each stamp and signature, and five downloadable files. The document is also saved in a searchable archive.

Behind that one click, the image passes through 13 steps. Two of them use models someone else trained (IndicOCR for reading, a YOLOv8 model for signatures). Everything else is code written for this project.

In one sentence: the image is read (IndicOCR), checked (YOLO + colour), mined for values (regex), cleaned of ID numbers (masking), summarised (verdict), drawn on (annotated picture), saved as files and in a database, and shown in tabs.

2. Every file and folder, and what it does

The project folder holds three kinds of things: the notebooks you run, the IndicOCR engine they load, and the documents (report, paper, slides). The app itself lives entirely inside one notebook, indic_ocr_colab.ipynb.

How the files connect

The notebook is the only thing you run. In cell 3 it downloads the indic-ocr folder from Hugging Face (snapshot_download("bodhan-ai/indic-ocr")). In cell 4 it adds that folder to Python's search path and imports IndicOCR from indic_ocr.py. From then on, one call, parser.parse(path), runs all the engine files in the order shown in section 5. Everything after OCR (marks, fields, masking, verdict, exports, archive, app) is plain Python inside the notebook cells S1, S2 and A1–A5.

4. One page, step by step

Follow one real example: the Marathi government order real_001.jpg with a table, a violet round seal and the officer's signature. Each step lists what goes in, what comes out, and where the code is.

1

Upload

InA photo or scan on the clerk's computer or phone
OutA file path on the server, plus the checkbox value mask = True
Codegr.Image(type="filepath"), gr.Checkbox, cell A5

The browser sends the image to the Gradio server running inside Colab. Gradio saves it as a temporary file and gives our function its path, a text string like /tmp/gradio/…/real_001.jpg. The "Mask Aadhaar / PAN numbers" box is ticked by default. Clicking Process calls process_document(path, mask).

If no image was uploaded, the function stops with the message "Upload a page image first." instead of crashing.

2

Normalise the image

InAny JPG/PNG, any size, any colour mode
Outapp_output/real_001/real_001_input.png, RGB, longest side ≤ 2000 px
Codeprocess_document part 0, cell A4

A folder /content/app_output/<name>/ is made for this document. The image is opened with Pillow and converted to RGB (three colour channels). If its longest side is more than 2000 pixels, thumbnail((2000, 2000)) shrinks it while keeping the shape. The result is saved as a PNG, and from here on every step uses this copy.

Why: phone photos can be 4000 px and crashed Colab's memory. The layout model looks at the page at 1024 × 1024 anyway, so 2000 px keeps plenty of detail. Test case TC04 shrinks a 2976 × 4209 page to 2000 px; TC05 leaves a 1240 × 1754 page unchanged.
3

Find the regions and their order (IndicDocLayout)

InThe normalised PNG
OutA list of blocks: box, label, type, confidence, reading order (text still empty)
Codeparser.parse → IndicDocLayout.detect, files idp_offline.py, idp_layout.py, idp_model_infer.py, idp_blocks.py

The page is resized to a square of 1024 × 1024 and turned into numbers between 0 and 1. The RT-DETR model (33 million parameters) looks at the whole page and makes a fixed set of guesses. Each guess has a box, a score for each of 37 labels, and a score for how it ranks against the others in reading order. Guesses with a score above the threshold are kept, and their order is decoded into a sequence.

The boxes come out on a 0–1000 scale as [y0, x0, y1, x1]. The code converts them to pixels on your image as [x0, y0, x1, y1] and clamps them inside the page. Then clean_layout removes duplicate boxes (one box at least 90% inside a similar one), keeps only the largest header and the largest footer, and drops empty header/footer frames. Finally the order is renumbered 0, 1, 2, … with no gaps.

In simple words: before reading anything, the system draws a rectangle around every paragraph, title and table and numbers them in the order a person would read them.
4

Read each region (IndicBlockOCR)

InThe page and its list of blocks
OutEvery block now has text; the page also has a Markdown version
CodeIndicBlockOCR.run, files idp_contract.py, idp_crops.py, idp_recognizer.py, idp_reconstruct.py
  1. Skip some blocks. Labels header, footer, diagram, image, chart and advertisement are not read. They stay in the list with empty text.
  2. Drop nested equations. An equation box at least 70% inside another block would be read twice, so it is removed.
  3. Crop. Each remaining block is cut out of the page with a few pixels of padding so letter edges are not clipped.
  4. Clamp the size. Each crop is scaled so its pixel area falls between a minimum and a maximum, keeping its shape. Tiny crops grow so letters are readable; huge or very long crops shrink so they don't turn into tens of thousands of image tokens.
  5. Choose the instruction. Tables get a "write this as an HTML table" prompt, equations a LaTeX prompt, everything else a plain transcription prompt.
  6. Generate the text. The crop and its prompt are put into the model's chat format. Several crops go to the GPU together. The 0.8B model writes the text one token at a time, always taking the most likely token (greedy), up to 2048 tokens, and stops at the tokenizer's end token.
  7. Put it back. Texts come back in the same order as the requests, so each text is attached to its block by position.
  8. Build Markdown. Block texts are joined in reading order. Words broken by a hyphen at a line end are rejoined, and Indian-script text inside maths is wrapped so it stays valid LaTeX.

Back in our notebook, every block text and the Markdown pass through clean(), which replaces the tokenizer's leftover space marker ▁ with a normal space.

Why it takes the longest: the model writes one token at a time, so more text means more time. This step is about 5.7 s of the 6.7 s average, and about 25 s on a dense page like real_001.jpg.
5

Find signatures and stamps

InThe normalised PNG
OutA list of marks: type, box, confidence, method
Codedetect_marks → yolo_boxes, colour_stamps, cell S2

Signatures: the YOLOv8s model looks at the page at 1024 px and returns boxes with a confidence. Boxes at 0.4 or above are kept as {"type": "signature", "method": "yolo"}.

Stamps: the colour method (details in section 6) finds large, roughly round or square blobs of strong colour. Each becomes {"type": "stamp", "conf": null, "method": "colour"}. If STAMP_WEIGHTS pointed to a trained stamp model, YOLO would be used here instead.

6

Merge marks with the text

InBlocks from step 4, marks from step 5
Outpage["marks"], crop images, inside_mark tags on blocks
Codedetect_marks and add_marks, cell S2
  • Rule a: a stamp blob more than 60% inside a signature box is thrown away. It is a blue-ink signature, not a stamp.
  • Rule c: every mark is cropped from the page and saved as crops/<name>_<type>_<i>.png.
  • Rule b: any text block more than 50% inside a mark gets "inside_mark": "stamp" (or signature). This flags seal text read as a garbage paragraph. The text is kept, never deleted.

"More than 60% inside" is measured with covered(a, b): the area of the overlap divided by the area of box a.

7

Extract key fields

InBlock texts in reading order
OutA list of [field, value] pairs
Codeto_plain, extract_fields, cell A2

All block texts are turned into plain text (tables become one line per row) and joined with new lines in reading order. Devanagari digits are swapped for Latin digits, 8 patterns are run, and duplicates are removed. Details in section 7.

8

Mask identity numbers

InFields, block texts, Markdown, full text, crops
OutThe same, with Aadhaar and PAN hidden; a list of black rectangles for the picture

Only if the checkbox is ticked. The black rectangles are worked out first, from the unmasked text. Then the fields, every block's text, the Markdown and the full text are masked, and the black rectangles are also painted on each mark crop, in case a number sits next to a signature. Details in section 8.

5. Inside IndicOCR: which file runs when

This is what happens inside the single call parser.parse(path). Two stages, with a list of blocks passed between them.

Why the text reader loads late: the parser.recognizer property creates the 0.8B model only the first time it is needed (lazy loading). That is why the first page of a session is slow, and why the fp16 setting must be changed before that first page.

Why we saw a footer problem: stage 1 labelled the officer's designation line at the bottom as a footer on 26 of 30 benchmark pages, and stage 2 skips footers by design. Those characters were never read, which raised our CER.

6. Signatures and stamps in detail

Signatures: a trained detector

Cell S1 downloads yolov8s.pt from tech4humans/yolov8s-signature-detector and loads it with Ultralytics. In S2, yolo_boxes(model, path, "signature", 0.4) runs model(path, conf=0.4, imgsz=1024) and turns each detected box into a dictionary with its rounded coordinates and confidence. Signatures are thin pen strokes, so the page is given to YOLO at 1024 px rather than the usual 640 px to keep the strokes visible.

Stamps: a colour rule, no training

Why colour works: office seals are pressed in blue, violet or red ink, while printed text is black. In HSV, "coloured" is one test on saturation. Why it fails: black stamps look exactly like text; faded stamps fall below S = 70; a stamp pressed over a blue signature can merge with it and be dropped by rule a; coloured logos can pass as stamps.

The containment test used by the merge

def covered(a, b):
    """Fraction of box a that lies inside box b."""
    x0, y0 = max(a[0], b[0]), max(a[1], b[1])
    x1, y1 = min(a[2], b[2]), min(a[3], b[3])
    inter = max(0, x1 - x0) * max(0, y1 - y0)
    area  = (a[2] - a[0]) * (a[3] - a[1])
    return inter / area if area else 0.0

Example: a text block of 100 × 20 lying fully inside a 200 × 200 stamp has covered = 1.0 but an IoU of only 0.05. That is why the merge uses containment ("is this small box part of that big one?") and the evaluation uses IoU ("do these two boxes match?").

7. Key-field extraction in detail

Building the text

to_plain cleans each block: <br> becomes a space, the end of a table cell becomes a space, the end of a table row becomes a new line, all other HTML tags are removed, entities like &amp; are decoded and $ signs from LaTeX are dropped. The blocks are joined with new lines in reading order into one string, full.

The digit swap

DEV_DIGITS = str.maketrans("०१२३४५६७८९", "0123456789"). Each Devanagari digit becomes one Latin digit, so the text keeps the same length and every position still points to the same character. Masking relies on that.

The 8 patterns (exact, from cell A2)

The "no digit before or after" checks (look-behind (?<!\d) and look-ahead (?!\d)) stop the PIN pattern from finding a 6-digit piece inside every 12-digit Aadhaar number.

Removing duplicates

Each value's spaces are tidied, and a set of (field, value) pairs remembers what was already added. A date written three times appears once.

Worked example (the notebook's own self-test)

→ Aadhaar 2345 6789 0123 · PAN ABCDE1234F · Phone 9876543210 · Date 12/03/2024
  · Survey / Gat no. गट नं. 45/2 · Amount ₹ 1,500

Result on the benchmark: 147 of 147 values, no wrong values. Known gaps: dates with a Marathi month name and landline numbers with an STD code (found on the real circular, test cases TC25 and TC23).

8. Privacy masking in detail

In the text

find_spans(text, ("Aadhaar", "PAN")) returns (kind, start, end) for each number. mask_text sorts them from the end of the text backwards and replaces each span with mask_value: spaces removed, Devanagari digits converted, only the last 4 characters kept.

Aadhaar 2345 6789 0123  →  XXXX XXXX 0123
PAN     ABCDE1234F      →  XXXXXX234F

Going backwards matters: the masked form can have a different length, and replacing from the front would shift every later position. Result: 33 of 33 numbers masked in text.

In the picture

Why the picture is harder than the text: the text knows exactly where the number is; the picture only knows the block's rectangle. Fix: find word boxes inside the block with a text detector such as CRAFT and paint the exact word.

10. The archive and search

Cell A3 opens /content/archive.db with one table:

CREATE TABLE docs(
  id INTEGER PRIMARY KEY, name TEXT, added TEXT,
  signed INT, stamped INT, fields TEXT, text TEXT)

Saving: archive_add inserts the name, the time, signed and stamped as 1/0, the fields as JSON and the masked full text after NFC normalisation.

Searching: archive_search(q) normalises the query to NFC and runs SELECT … WHERE text LIKE ? OR name LIKE ? ORDER BY id DESC with %q%. For each hit it cuts a snippet of about 60 characters on each side of the match and shows ✔ or ✘ for signed and stamped. The ? placeholders keep the query safe from SQL injection.

Why NFC: the same Marathi word can be stored as different code sequences. Normalising both the stored text and the query makes them identical, so the search finds it.

Limits: the file lives in /content and disappears when Colab restarts (point it to Google Drive or a server to keep it), and LIKE scans every row with no ranking. For a big office: PostgreSQL or SQLite FTS5 full-text search.

13. How we tested it

What the generator draws on each page: an office header, a title, a paragraph, field lines (name, date, random Aadhaar, PAN, phone, PIN, fee, survey number, email), a table on half of the pages, a signature with 85% chance (cursive-font name or scribble, blue or black, rotated ±8°) and a stamp with 85% chance (round or rectangular, blue/violet/red or black, faded, rotated ±25°, often over the signature). Half the pages get a lighting gradient, yellow tint, noise, blur and JPEG compression. Because the generator draws everything, it also writes down the exact answer for each page.

The speed notebook akshardrishti_speed_benchmark.ipynb builds the same pages (P1), wraps the recognizer with settings you can change and a timer (P2), tries one change at a time on 10 pages (P3), then runs the fastest setting that keeps CER within 0.005 of the original on all 30 pages (P4). That is how fp16 and cross-page batching were found.

14. Where the time goes

  • Why bf16 was slow: the T4 has no hardware support for bf16, so it runs through slow paths. fp16 runs on its tensor cores. Same CER and WER.
  • Why a dense page is slower: the reader writes one token at a time (about 34 tokens per average block). real_001.jpg took about 25 s.
  • Batching: blocks from 15 pages in the same GPU calls → 1.46 s per page parser time. 30 pages → 2.19 s (more memory and padding).
  • Memory: peak about 3.2 GB of the T4's 16 GB.

16. Glossary

BlockOne region of the page found by the layout model: a paragraph, title, table and so on.
Bounding boxA rectangle [x0, y0, x1, y1] in pixels: top-left and bottom-right corners.
ContainmentThe fraction of box a that lies inside box b. Used by the merge rules.
IoUOverlap divided by combined area of two boxes. Used to score detections.
TokenA small piece of text the model writes in one step.
Greedy decodingAlways choosing the most likely next token, so the result is the same every run.
HSVColour described as hue (which colour), saturation (how strong) and value (how bright).
Morphological closingGrow then shrink a mask so nearby strokes join into one shape.
RegexA pattern for finding text, such as "5 capital letters, 4 digits, 1 capital letter".
NFCA Unicode normal form that makes equivalent character sequences identical.
fp16 / bf16Two 16-bit number formats. The T4 runs fp16 fast and bf16 slowly.
CER / WERCharacter / word error rate: edits needed to fix the output, divided by the length of the correct text.
Ground truthThe correct answer. Our generator records it while drawing each page.
